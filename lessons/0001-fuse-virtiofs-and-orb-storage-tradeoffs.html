FUSE, virtiofs & Orb Storage Trade-Offs

Why your homelab orbs share ZFS datasets over FUSE, why UID 2000 mattered, and why "pause" is a clean cold poweroff.

Mission tie-in: Structuring reusable NixOS modules across diverse storage models without leaky abstractions (ADR-0006 on homelab).  ·  Reading time: ~5 min + 3 retrieval checks.

1. What FUSE Actually Is

Normally, a Linux filesystem driver (like ext4 or ZFS) runs inside the kernel. When a process calls open() or read(), the kernel talks straight to the disk driver.

FUSE (Filesystem in Userspace) splits that in two: the kernel keeps a minimal stub filesystem and forwards every file operation as a message to a regular userspace daemon.[1] That daemon can back the files with anything—an SSH server (sshfs), an S3 bucket, or a directory on a VM host.

virtiofs takes the exact same FUSE protocol and replaces local /dev/fuse with a shared-memory virtqueue crossing the VM boundary.[2] The guest kernel acts as the FUSE client; virtiofsd on homelab acts as the FUSE server.

2. The Three Architectural Trade-Offs

Knowing that virtiofs is a stateful FUSE bridge explains all three major storage decisions in ADR-0006.

Trade-Off A: ZFS Dataset + virtiofs vs. ZFS ZVOL + virtio-blk

OpenZFS offers two dataset kinds: a filesystem dataset (POSIX directory tree) and a ZVOL (a raw block device at /dev/zvol/...).[4]

Dimension ZFS Dataset + virtiofs Chosen ZFS ZVOL + virtio-blk
Host visibility Host can read, git diff, and copy files live while the orb runs. Guest owns an opaque ext4/xfs block device; host mounting it live causes corruption.
Isolation boundary Wider: guest sends rich FUSE syscalls parsed by virtiofsd on host. Narrower: guest only reads/writes numbered disk blocks.
Space & tuning Dynamic recordsize; consumes only bytes written (capped by quota=20G). Fixed volblocksize set at creation; thick-provisioned unless sparse (-s).

Why this won: On a single-user homelab, inspecting a stuck agent's workspace directly from the host is huge leverage—and ADR-0005 already accepted the virtiofs trust boundary for sharing /nix/.ro-store.

Trade-Off B: Clean Poweroff vs. RAM Snapshot/Restore

Why did our resume take ~8 seconds (cold Linux + NixOS boot) instead of <500 ms via cloud-hypervisor snapshot/restore?

Because FUSE is stateful. The guest kernel holds cached nodeids and open file descriptors that only have meaning inside the running virtiofsd process's in-memory table.[3] If you snapshot VM RAM and stop virtiofsd, restoring that RAM against a fresh virtiofsd breaks every open file unless the hypervisor and virtiofsd coordinate explicit DEVICE_STATE serialization (find-paths or file-handles).[3]

Pause Strategy Resume Speed RAM Held While Paused Complexity / Failure Mode
Clean poweroff Chosen ~8s cold boot 0 MB (slot freed) Lowest: ZFS unmounts cleanly; any free slot can resume it.
CH pause Instant Full 4 GB + slot Defeats the 4-slot cap; can't keep 20 idle repos paused.
RAM snapshot <1s 0 MB (4 GB on disk) High: requires verified DEVICE_STATE in both CH and virtiofsd; stale FUSE handles silently break if omitted.

Trade-Off C: Pinned UID 2000 + --sandbox=none vs. Namespace UID Mapping

When we first deployed to homelab, NixOS warned it wouldn't change existing agent-vm from UID 975 to 2000. Because agent-vm-launcher.nix runs virtiofsd --sandbox=none as unprivileged agent-vm, virtiofsd exposes host files with their real numeric UID/GID.

The Security Seam
virtiofsd's default --sandbox=namespace uses pivot_root(2) to jail the daemon inside the shared directory,[5] which requires user namespaces or root privileges. Running unprivileged as agent-vm with --sandbox=none is simpler and relies on Linux DAC permissions (agent-vm can only read/write paths owned by UID 2000 or world-readable like /nix/store). The trade-off: guest user and host agent-vm must share the exact same numeric UID/GID (2000).
