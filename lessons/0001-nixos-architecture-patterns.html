Multi-Device NixOS Architecture

Lesson 0001 • Core Patterns, Storage Seams, and Ground Truth Verification

In this lesson, we break down the four core architectural patterns that transformed a monolithic 420-line server script into a modular, multi-device NixOS codebase ready for Raspberry Pis, Jetson Orin nodes, and high-spec servers.

1. The Four Foundational Patterns

Pattern 1: The Storage Seam (Host Property vs Application Property)

The Mistake: Putting environment.persistence."/persist" inside reusable service modules (e.g. immich.nix, nextcloud.nix).

The Law: Ephemeral root filesystems (ZFS rollback, tmpfs root) are a property of the host machine's storage architecture, not the applications. When persistence is centralized in hosts/homelab/persistence.nix:

  • Service modules remain 100% pure and portable.
  • Standard vanilla Nixpkgs services can be enabled with zero custom wrapping.
  • Non-impermanence devices (RPi5 on SD card, Orin on NVMe) can import the exact same modules without crashing.
Pattern 2: The Core → Profile → Host Hierarchy

NixOS systems should be assembled as clean layer cakes rather than copy-pasted monolithic files:

  • modules/core/base.nix: Universal baseline across all hardware (user accounts, SSH keys, locale, timezone, core tools, flake settings).
  • modules/profiles/*.nix: Composed functional roles (e.g. server.nix for power inhibitors and Tailscale; desktop.nix for GNOME, GDM, and PipeWire).
  • hosts/<name>/configuration.nix: Lean composition manifest (~100-150 lines) specifying hardware IDs, storage disks, profile imports, and enabled service toggles.
Pattern 3: Inverted Routing Contracts (Decentralized Caddy)

The Mistake: A single central reverse proxy file (caddy.nix) hardcoding a 250-line list of all virtual hosts, ports, and subdomains.

The Law: The webserver engine (Caddy) should provide the global infrastructure (TLS, PKI, firewall, landing page), while each individual service module registers its own services.caddy.virtualHosts."${cfg.subdomain}.${caddy.domain}" block when enabled.

Result: Adding or removing a service is a 1-file change with complete locality.

Pattern 4: Declarative Symlink Lifecycles vs Imperative Hacks

The Mistake: Using sed or manual symlink edits in live directories to fix Nextcloud upgrade errors.

The Law: systemd-tmpfiles does not re-evaluate existing files during a live nixos-rebuild switch. When modifying declarative override configs, ensure the systemd service setup lifecycle explicitly refreshes tmpfiles:

systemd.services.nextcloud-setup.preStart = ''
  ${pkgs.systemd}/bin/systemd-tmpfiles --create --prefix=${cfg.dataDir}/config
'';

2. Why Double-Checking and Cold Reboots Matter

"The Live Switch Fallacy": nixos-rebuild switch only reloads modified systemd units. It does not prove your machine will survive a cold boot.

In a declarative ephemeral setup, a cold reboot is the only way to verify:

  1. Initrd Post-Device Hooks: Does zfs rollback -r rpool/nixos/empty@start wipe the root cleanly before mount?
  2. Mount Order Dependencies: Do neededForBoot = true; and nofail prevent boot hanging on ZFS pool imports?
  3. State Restoration: Did bind-mounts in /persist correctly restore database files and SSL certificates?
  4. Telemetry & Power: Did hdparm -S 180 properly set the hardware controller standby timeout across SATA drives?
