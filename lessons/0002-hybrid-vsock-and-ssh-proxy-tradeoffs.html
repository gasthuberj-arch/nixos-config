Hybrid vsock & Out-of-Band SSH Trade-Offs

How orb attach opens a shell inside a microVM with zero TCP ports, zero IP routing, and Unix-socket access control.

Mission tie-in: Keeping host-to-guest control paths decoupled from guest networking and firewall policy (ADR-0006 on homelab).  ·  Reading time: ~5 min + 3 retrieval checks.

1. How Hybrid vsock Connects Host to Guest

AF_VSOCK is a Linux socket address family built specifically for VM-to-host communication.[1] Instead of an IP address and port, an endpoint is identified by a 32-bit Context Identifier (CID) (e.g., 10 + slot) and a port number—bypassing Ethernet, IP routing, ARP, and firewall rules completely.

Cloud Hypervisor (following Firecracker) uses a hybrid vsock design:[2] inside the guest, applications use standard AF_VSOCK (sshd listens on vsock::22), while on the host, Cloud Hypervisor exposes a plain Unix domain socket (/run/orbs/slot1/vm/notify.vsock). To reach guest port 22, the host client connects to that Unix socket and writes a one-line text handshake: CONNECT 22\n.[2]

On your homelab, orb.sh delegates that handshake to systemd-ssh-proxy via ssh -o ProxyCommand="systemd-ssh-proxy %h %p" -o ProxyUseFdpass=yes user@vsock-mux/run/orbs/slot1/vm/notify.vsock.[3] Once the handshake succeeds, systemd-ssh-proxy hands the connected file descriptor directly to ssh and exits—leaving zero proxy process overhead during your session.

2. The Three Architectural Trade-Offs

Trade-Off A: AF_VSOCK SSH vs. TCP SSH on br-agent

Dimension AF_VSOCK Only Chosen TCP Port 22 on 10.240.0.(10+N)
Attack surface Zero TCP ports listening inside the guest; sibling orbs on br-agent cannot reach each other's sshd. Exposes TCP:22 on the bridge; requires extra nftables rules to stop orb-to-orb SSH probing.
Failure isolation Works even when guest networking is down, misconfigured, or offline. If systemd-networkd or the TAP fails, you lose SSH access too.
Reachability Host-only (must SSH to homelab first, then orb attach, with -L for port forwarding). Directly reachable over IP if routed or proxied via Caddy.

Trade-Off B: Hybrid vsock (AF_UNIX) vs. Kernel vhost_vsock

Traditional QEMU/KVM uses the host kernel's vhost_vsock module, where host processes open real AF_VSOCK sockets addressed by global CID. Cloud Hypervisor's hybrid model maps each VM's vsock to a plain host Unix socket instead.[2]

  • What you gain: Standard Linux filesystem permissions (/run/orbs/slot1/vm is 0700 owned by agent-vm) govern who can connect; no host kernel vhost_vsock module needed; no risk of CID collisions across unrelated VMMs.
  • What you pay: Standard AF_VSOCK host tools can't connect directly—the host client must understand the CONNECT <port>\n framing (which systemd-ssh-proxy's vsock-mux/ scheme solves natively).[3]

Trade-Off C: Explicit sshd.socket + systemd.ssh_auto=no vs. Systemd Auto-Binding

Why Two Lines in agent-worker.nix Matter
Since systemd v256, systemd-ssh-generator automatically detects VMs with AF_VSOCK and binds its own sshd-vsock.socket to vsock:22.[4] If left enabled, it collides with NixOS's sshd.socket—or silently accepts connections with systemd's default key handling instead of our locked-down AllowUsers = ["user"], PermitRootLogin = "no", and /run/orb-job/authorized_keys. Passing systemd.ssh_auto=no disables the generator, and socketConfig.ListenStream = lib.mkForce ["vsock::22"] replaces (rather than appends to) the default TCP [::]:22 listener.
